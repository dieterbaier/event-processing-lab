== 1. Introduction and Goals

=== 1.1. Purpose

The Event Processing Lab is a **hands-on learning project** designed to enable integration architects to gain practical experience with different event processing technologies through a common use case: order lifecycle event processing.

By implementing the same business scenarios across multiple technologies (Kafka, Esper, Apache Flink, Flink CEP), this project provides a direct comparison framework for evaluating:

* Architectural trade-offs
* Scalability characteristics  
* Operational complexity
* State handling approaches
* Rule/pattern complexity
* Development experience

== 2. Architecture Constraints

=== 2.1. Technical Constraints

* **Java 21**: The project uses Java 21 features and compatibility
* **Gradle**: Build tool for multi-module project management
* **Kafka**: Apache Kafka 3.6.1 as the event backbone
* **Esper**: Esper 8.7.0 for lightweight CEP
* **Flink**: Apache Flink 1.17.1 for distributed stream processing
* **Flink CEP**: Flink CEP 1.17.1 for pattern detection

=== 2.2. Organizational Constraints

* Learning-focused rather than production-ready
* Minimal dependencies preferred (plain Java over Spring Boot)
* Clear separation between technology implementations for comparison
* JSON serialization for human readability and debugging

=== 2.3. Conventions

* Follow SOLID principles
* Use Domain-Driven Design ubiquitous language
* Include semantic anchors for cross-referencing
* Document all architectural decisions in ADRs
* Maintain traceability between documentation elements

== 3. System Scope and Context

=== 3.1. Business Context

The Event Processing Lab demonstrates a simplified order lifecycle management system where:

. Customers place orders
. Payments are processed
. Orders are either fulfilled or cancelled
. Shipments are initiated for fulfilled orders

This provides a realistic foundation for exploring event processing concepts while maintaining simplicity for learning purposes.

=== 6.2. Error Scenarios

==== 6.2.1. Event Deserialization Failure

*Cause:* Malformed JSON or unknown event type
*Detection:* EventSerializer.deserialize() throws exception
*Handling:* Log error, skip event, continue processing
*Impact:* Single event loss, processing continues
*Recovery:* Fix event format, replay from offset

==== 6.2.2. Kafka Connection Failure

*Cause:* Kafka broker unavailable
*Detection:* Kafka client throws exception
*Handling:* Retry with exponential backoff, log error
*Impact:* Processing paused until connection restored
*Recovery:* Restart consumers when Kafka available

==== 6.2.3. Esper Rule Compilation Error

*Cause:* Invalid EPL syntax
*Detection:* Exception during EPL statement creation
*Handling:* Fail fast, log detailed error
*Impact:* Engine fails to start
*Recovery:* Fix EPL syntax, restart engine

== 8. Cross-Cutting Concepts

=== 8.1. Threat Model [semantic-anchor: risk.state-explosion]

| ID | Threat | Category | Severity | Mitigation |
|----|--------|----------|----------|------------|
| T-001 | State explosion in CEP engines [semantic-anchor: risk.state-explosion] | Denial of Service | High | Limit window sizes, use efficient patterns, monitor state size |
| T-002 | Unauthorized access to Kafka | Information Disclosure | Medium | Configure ACLs, use TLS, authenticate clients |
| T-003 | Event spoofing | Spoofing | Medium | Validate event signatures, use trusted sources |
| T-004 | Data leakage between consumers | Information Disclosure | Low | Use separate consumer groups, proper authorization |
| T-005 | Technology compatibility issues [semantic-anchor: risk.technology-compatibility] | Tampering | Medium | Use stable versions, test integration, monitor dependencies |

=== 8.2. Security

* **Kafka Security**: Configure TLS for encryption, SASL for authentication, ACLs for authorization
* **Event Validation**: Validate event structure and content before processing
* **Logging Security**: Sanitize sensitive data in logs (payment details, PII)
* **Dependency Security**: Use trusted repositories, verify dependency checksums

|----------|-----------|--------------|
| Use Kafka as Event Backbone | High throughput, fault tolerance, scalability, ecosystem | More operational complexity, resource usage |
| Use JSON Serialization | Human-readable, easy to debug, widely supported | Larger message size, slower parsing |
| Use Plain Java | Focus on core concepts, reduce dependencies | Less production-ready, manual configuration |
| Separate Implementations | Direct comparison, no abstraction leakage | Some code duplication, maintenance overhead |
