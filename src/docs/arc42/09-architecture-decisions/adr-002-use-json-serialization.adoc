[[adr-002-use-json-serialization]]
== ADR-002: Use JSON Serialization for First Iteration



=== Status

[.status-accepted]
Accepted

=== Context

The Event Processing Lab needs a serialization format for events transmitted through the Kafka event backbone. The serialization format must:

* Be readable by all processing engines (Esper, Flink, custom consumers)
* Support all event types (OrderCreated, PaymentReceived, PaymentFailed, OrderCancelled, ShipmentStarted)
* Enable easy debugging and understanding of event content
* Be extensible for future event types
* Work well with Kafka's message format

=== Decision

*Use JSON (JavaScript Object Notation) as the serialization format for the first iteration of the Event Processing Lab.*

=== Alternatives Considered

==== 1. JSON [.selected]#✅ Selected#

*Pros:* Human-readable, easy to debug, widely supported, schema-flexible, language-agnostic

*Cons:* Verbose (larger message size), no built-in schema validation, slower parsing than binary formats

*Libraries:* Jackson, Gson, JSON-B (Java), native support in most languages

==== 2. Apache Avro

*Pros:* Compact binary format, schema evolution support, built-in validation, efficient serialization

*Cons:* Less human-readable, requires schema registry, more complex setup

*Libraries:* Avro Java library, Confluent Schema Registry

==== 3. Protocol Buffers (Protobuf)

*Pros:* Compact binary format, very fast serialization/deserialization, strong typing

*Cons:* Less human-readable, requires .proto file definitions, schema management

*Libraries:* protobuf-java, good ecosystem

==== 4. Apache Thrift

*Pros:* Binary format, schema evolution, multiple language support

*Cons:* Less human-readable, complex IDL, decreasing popularity

*Libraries:* Thrift Java library

==== 5. Java Serialization

*Pros:* Native Java support, simple to implement

*Cons:* Java-only, not human-readable, security issues, version compatibility problems

*Libraries:* Built into Java

=== Consequences

==== Positive Consequences

. *Human Readability*: JSON events can be easily read and understood by humans, making debugging and learning much easier.
. *Universal Support*: JSON is supported by virtually all programming languages and technologies, ensuring compatibility across all processing engines.
. *Debugging Friendly*: Events can be inspected using simple text editors, command-line tools, or browser-based tools without requiring specialized software.
. *Easy to Learn*: JSON is a widely known format, reducing the learning curve for understanding event content.
. *Schema Flexibility*: JSON allows for easy addition of new fields and event types without requiring schema updates.
. *Integration Simplicity*: Most Kafka clients and processing engines have built-in or easy JSON support.

==== Negative Consequences

. *Message Size*: JSON is more verbose than binary formats, resulting in larger message sizes and potentially lower throughput.
. *Parsing Performance*: JSON parsing is slower than binary serialization, which may impact performance at very high throughput.
. *No Schema Validation*: Without additional tooling, there's no built-in validation of event structure.
. *No Type Safety*: JSON doesn't preserve type information, requiring careful handling in consuming applications.
. *Schema Evolution Complexity*: While flexible, managing schema changes across multiple consumers can become complex without a schema registry.

=== Future Considerations

For production scenarios or high-throughput requirements, consider migrating to:

. *Apache Avro*: If schema evolution and validation are critical
. *Protocol Buffers*: If performance is paramount and human readability is less important
. *Hybrid Approach*: Use JSON for development/learning, Avro/Protobuf for production benchmarks

This migration would be documented in a new ADR and would maintain backward compatibility where possible.
