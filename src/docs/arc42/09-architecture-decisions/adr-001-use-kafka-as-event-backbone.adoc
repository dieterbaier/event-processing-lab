[[adr-001-use-kafka-as-event-backbone]]
= ADR-001: Use Kafka as Event Backbone

[semantic-anchor: decision.kafka-as-event-backbone]

== Status

[.status-accepted]
Accepted

== Context

The Event Processing Lab needs a central event transport mechanism to connect event producers with various event processing engines (Kafka Consumer, Esper CEP, Flink, Flink CEP). This event backbone must:

* Support high throughput for event streaming
* Provide fault tolerance and durability
* Enable horizontal scalability
* Support multiple concurrent consumers
* Maintain event ordering within logical partitions

== Decision

*Use Apache Kafka as the event backbone for the Event Processing Lab.*

== Alternatives Considered

=== 1. Apache Kafka [.selected]#✅ Selected#

*Pros:*
- High throughput, fault tolerant, horizontally scalable, built-in partitioning, excellent ecosystem, strong community

*Cons:*
- More complex to operate, requires ZooKeeper/KRaft, higher resource usage

*Integration:* Native support in Flink, good Java client, widely supported

=== 2. RabbitMQ

*Pros:* Simple to set up and operate, lightweight, good Java support

*Cons:* Lower throughput than Kafka, less suitable for event streaming, no built-in partitioning

*Integration:* Would require custom integration with Flink

=== 3. Apache Pulsar

*Pros:* High throughput, multi-tenancy, built-in functions, good ecosystem

*Cons:* Less mature than Kafka, smaller community, more complex setup

*Integration:* Good Java client, Flink connector available

=== 4. NATS / NATS Streaming

*Pros:* Extremely lightweight, high performance, simple protocol

*Cons:* Less Java ecosystem support, newer streaming capabilities

*Integration:* Limited Flink integration

== Consequences

=== Positive Consequences

. *High Throughput*: Kafka can handle hundreds of thousands of events per second, enabling realistic performance testing of CEP engines.
. *Fault Tolerance*: Kafka's replication ensures events are not lost even if nodes fail, providing reliable event transport for learning scenarios.
. *Horizontal Scalability*: Kafka scales horizontally by adding more brokers, allowing us to demonstrate scaling characteristics.
. *Multiple Consumer Support*: Kafka's consumer group model allows each processing engine (Esper, Flink, etc.) to consume events independently at their own pace.
. *Ordering Guarantees*: Kafka maintains strict ordering within partitions, which is important for event pattern detection.
. *Ecosystem Integration*: Kafka has excellent integration with Flink (native connector) and good Java client support for Esper and custom consumers.
. *Industry Relevance*: Kafka is widely adopted in industry, making the learning experience directly applicable to real-world scenarios.

=== Negative Consequences

. *Operational Complexity*: Running Kafka requires understanding of brokers, topics, partitions, consumer groups, and configuration options.
. *Resource Usage*: Kafka requires more resources (memory, disk) than lighter alternatives like RabbitMQ.
. *Setup Overhead*: Requires additional setup (ZooKeeper or KRaft mode) compared to simpler message brokers.
. *Learning Curve*: Users need to understand Kafka concepts before effectively using the event backbone.
