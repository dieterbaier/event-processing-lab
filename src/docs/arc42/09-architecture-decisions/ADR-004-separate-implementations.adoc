[[adr-004-separate-implementations]]
= ADR-004: Separate Esper and Flink Implementations

[semantic-anchor: decision.separate-implementations]

== Status

[.status-accepted]
Accepted

== Context

The Event Processing Lab needs to decide how to structure the implementations of the different event processing technologies (Esper CEP, Flink Basic, Flink CEP). The main approaches are:

* Shared codebase with abstraction layer
* Separate implementations with direct technology access
* Hybrid approach with some shared components

This decision impacts:

* Direct comparison capability
* Code duplication
* Maintenance effort
* Learning clarity
* Architectural consistency

== Decision

*Maintain separate implementations for Esper and Flink to enable direct comparison.*

== Alternatives Considered

=== 1. Separate Implementations [.selected]#✅ Selected#

*Pros:*
- Direct comparison of technologies without abstraction interference
- Each technology can be implemented using its native patterns and best practices
- Clear demonstration of each technology's unique capabilities
- No abstraction leakage or "lowest common denominator" effect
- Better for learning each technology's true nature

*Cons:*
- Some code duplication (event consumption, basic utilities)
- More maintenance overhead
- Potential for inconsistent patterns across modules

*Implementation:* Each technology in its own module with minimal shared code

=== 2. Shared Abstraction Layer

*Pros:*
- Maximum code reuse
- Consistent interfaces across technologies
- Less total code to maintain
- Easier to swap implementations

*Cons:*
- Abstraction may hide important technology differences
- Lowest common denominator approach limits capabilities
- Harder to see each technology's unique features
- Abstraction leakage is inevitable

*Implementation:* Common interface with technology-specific implementations

=== 3. Hybrid Approach

*Pros:*
- Some reuse for common functionality
- Still allows technology-specific optimizations
- Balance between reuse and clarity

*Cons:*
- More complex architecture
- Decisions about what to share vs. separate can be difficult
- May still have abstraction issues

*Implementation:* Shared utilities, separate processing logic

== Consequences

=== Positive Consequences

. *Direct Comparison*: Each technology can be evaluated on its own merits without abstraction interference.
. *Technology Authenticity*: Each implementation uses the technology's native patterns and best practices.
. *Clear Demonstration*: Unique capabilities of each technology are clearly visible.
. *Learning Effectiveness*: Students can understand each technology's true approach and philosophy.
. *Architecture Clarity*: No hidden abstractions or conceptual gaps.

=== Negative Consequences

. *Code Duplication*: Common functionality (Kafka consumption, logging) may be duplicated.
. *Maintenance Overhead*: More modules to maintain and keep consistent.
. *Potential Inconsistency*: Different patterns and approaches across modules.
. *Larger Codebase*: More total code to understand and navigate.
