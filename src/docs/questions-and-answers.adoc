== Answered Questions

=== Project Scope

[cols="1,3,2", options="header"]
|===
| ID
| Question
| Answer

| Q-SCOPE-001
| Why did we choose the order lifecycle use case?
| It provides a clear, relatable business scenario with well-defined events and workflows that can be implemented across all technologies

| Q-SCOPE-002
| Why are we comparing these specific technologies?
| They represent different approaches to event processing: message broker (Kafka), lightweight CEP (Esper), distributed processing (Flink), and pattern detection library (Flink CEP)

| Q-SCOPE-003
| Why is this a learning project rather than a production system?
| The focus is on understanding architectural trade-offs and technology capabilities, not on production-grade features like fault tolerance, security, and scalability at enterprise scale
|===

=== Technology Decisions

[cols="1,3,2", options="header"]
|===
| ID
| Question
| Answer

| Q-TECH-004
| Why did we choose Kafka as the event backbone?
| Kafka provides high throughput, fault tolerance, scalability, and excellent ecosystem support. Pugh Matrix analysis showed it scored highest among alternatives (RabbitMQ, Pulsar, NATS)

| Q-TECH-005
| Why JSON serialization instead of binary formats?
| JSON is human-readable, easy to debug, and widely supported. For a learning project, readability and ease of use are more important than serialization efficiency

| Q-TECH-006
| Why plain Java over Spring Boot?
| To focus on core concepts without framework overhead. Spring Boot adds complexity that obscures the underlying technology capabilities

| Q-TECH-007
| Why separate Esper and Flink implementations?
| To enable direct comparison without abstraction leakage. Shared interfaces are in the event-model module, but processing logic remains separate
|===
