# ADR-001: Use Kafka as Event Backbone

[semantic-anchor: decision.kafka-as-event-backbone]

## Status
✅ Accepted

## Context

The Event Processing Lab needs a central event transport mechanism to connect event producers with various event processing engines (Kafka Consumer, Esper CEP, Flink, Flink CEP). This event backbone must:

- Support high throughput for event streaming
- Provide fault tolerance and durability
- Enable horizontal scalability
- Support multiple concurrent consumers
- Maintain event ordering within logical partitions

## Decision

**Use Apache Kafka as the event backbone for the Event Processing Lab.**

## Decision Drivers

| Driver | Importance | Notes |
|--------|------------|-------|
| Throughput | High | Must handle high event volumes for realistic testing |
| Fault Tolerance | High | Events must not be lost during processing |
| Scalability | High | Must scale horizontally to handle increased load |
| Multiple Consumers | High | Different processing engines need independent access |
| Ordering Guarantees | Medium | Events should be processed in order within partitions |
| Ecosystem | Medium | Good integration with other technologies (Flink, etc.) |
| Learning Value | High | Kafka is widely used, understanding it is valuable |

## Alternatives Considered

### 1. Apache Kafka ✅ Selected
- **Pros**: High throughput, fault tolerant, horizontally scalable, built-in partitioning, excellent ecosystem, strong community
- **Cons**: More complex to operate, requires ZooKeeper/KRaft, higher resource usage
- **Integration**: Native support in Flink, good Java client, widely supported

### 2. RabbitMQ
- **Pros**: Simple to set up and operate, lightweight, good Java support
- **Cons**: Lower throughput than Kafka, less suitable for event streaming, no built-in partitioning
- **Integration**: Would require custom integration with Flink

### 3. Apache Pulsar
- **Pros**: High throughput, multi-tenancy, built-in functions, good ecosystem
- **Cons**: Less mature than Kafka, smaller community, more complex setup
- **Integration**: Good Java client, Flink connector available

### 4. NATS / NATS Streaming
- **Pros**: Extremely lightweight, high performance, simple protocol
- **Cons**: Less Java ecosystem support, newer streaming capabilities
- **Integration**: Limited Flink integration

## Consequences

### Positive Consequences

1. **High Throughput**: Kafka can handle hundreds of thousands of events per second, enabling realistic performance testing of CEP engines.

2. **Fault Tolerance**: Kafka's replication ensures events are not lost even if nodes fail, providing reliable event transport for learning scenarios.

3. **Horizontal Scalability**: Kafka scales horizontally by adding more brokers, allowing us to demonstrate scaling characteristics.

4. **Multiple Consumer Support**: Kafka's consumer group model allows each processing engine (Esper, Flink, etc.) to consume events independently at their own pace.

5. **Ordering Guarantees**: Kafka maintains strict ordering within partitions, which is important for event pattern detection.

6. **Ecosystem Integration**: Kafka has excellent integration with Flink (native connector) and good Java client support for Esper and custom consumers.

7. **Industry Relevance**: Kafka is widely adopted in industry, making the learning experience directly applicable to real-world scenarios.

### Negative Consequences

1. **Operational Complexity**: Running Kafka requires understanding of brokers, topics, partitions, consumer groups, and configuration options.

2. **Resource Usage**: Kafka requires more resources (memory, disk) than lighter alternatives like RabbitMQ.

3. **Setup Overhead**: Requires additional setup (ZooKeeper or KRaft mode) compared to simpler message brokers.

4. **Learning Curve**: Users need to understand Kafka concepts before effectively using the event backbone.

## Risk Mitigations

| Risk | Mitigation | Status |
|------|------------|--------|
| Complexity overwhelming learners | Provide simple Docker Compose setup, pre-configured topics | ✅ Implemented |
| Performance bottlenecks | Use appropriate partitioning strategy, monitor throughput | ⚠️ Monitor |
| Data loss during development | Configure appropriate replication factors, use durable commits | ✅ Implemented |
