# ADR-004: Separate Esper and Flink Implementations for Comparison

[semantic-anchor: decision.separate-implementations]

## Status
✅ Accepted

## Context

The Event Processing Lab aims to compare different event processing technologies (Kafka, Esper, Apache Flink, Flink CEP) from an integration architect's perspective. A key decision is how to structure the implementations of Esper and Flink to enable effective comparison.

The options are:
1. **Separate Implementations**: Maintain completely independent implementations for each technology
2. **Unified Abstraction**: Create a common abstraction layer that both Esper and Flink implement
3. **Shared Components**: Share some components (like event parsing) but keep processing logic separate

## Decision

**Maintain separate implementations for Esper and Flink, with a shared event model, to enable direct comparison while minimizing unnecessary duplication.**

## Decision Drivers

| Driver | Importance | Notes |
|--------|------------|-------|
| Direct Comparison | High | Must be able to compare technologies apples-to-apples |
| Learning Value | High | Clear understanding of each technology's unique approach |
| Code Clarity | High | Each implementation should be self-contained and easy to understand |
| Avoid Abstraction Leak | High | Abstractions often hide important differences |
| Maintainability | Medium | Balance between duplication and abstraction |
| Reusability | Medium | Some shared components are beneficial |

## Alternatives Considered

### 1. Separate Implementations ✅ Selected
- **Pros**: Direct comparison, no abstraction leakage, clear technology demonstration, easy to understand
- **Cons**: Some code duplication, harder to maintain if changes affect both
- **Structure**: Shared event-model, separate processing modules

### 2. Unified Abstraction
- **Pros**: Minimal code duplication, consistent interfaces, easier maintenance
- **Cons**: Hides technology differences, abstraction may not fit all use cases, reduces learning value
- **Structure**: Common CEP interface, Esper and Flink as implementations

### 3. Shared Components with Separate Processing
- **Pros**: Balance between reuse and separation, share only truly common code
- **Cons**: Need to carefully decide what to share, may still have duplication
- **Structure**: Shared event parsing/serialization, separate processing logic

## Consequences

### Positive Consequences

1. **Direct Comparison Enabled**: Each technology's implementation can be examined side-by-side without abstraction layers obscuring the differences.

2. **Clear Learning Value**: Learners can see exactly how each technology approaches the same problem, understanding the unique concepts and APIs.

3. **No Abstraction Leakage**: Important differences in how Esper and Flink handle events, state, patterns, etc. are fully visible.

4. **Flexible Experimentation**: Each implementation can be modified independently to test different approaches without affecting others.

5. **Technology-Specific Optimization**: Each implementation can be optimized for its specific technology without compromising the abstraction.

6. **Clear Responsibility**: Each module has a single, clear purpose and technology focus.

### Negative Consequences

1. **Code Duplication**: Some common functionality (like event deserialization) may be duplicated across modules.

2. **Maintenance Overhead**: Changes that affect multiple modules need to be applied to each separately.

3. **Inconsistency Risk**: Different implementations might handle edge cases differently.

4. **Integration Testing Complexity**: Testing interactions between modules may be more complex.

## Shared Components

While implementations are separate, the following will be shared:

1. **Event Model** (`event-model` module):
   - Event DTOs (OrderCreated, PaymentReceived, etc.)
   - Event serialization/deserialization (JSON)
   - Event type enumeration
   - Common utilities

2. **Kafka Configuration**:
   - Topic names
   - Bootstrap servers configuration
   - Common Kafka settings

3. **Testing Utilities**:
   - Test event generators
   - Common test assertions
   - Test configuration

## Comparison Patterns

The following patterns will be implemented separately in each technology to enable comparison:

### 1. Order Creation Processing [semantic-anchor: scenario.order-creation]
- **Esper**: EPL rule to detect OrderCreated events
- **Flink**: DataStream processing of OrderCreated events
- **Flink CEP**: Pattern to match OrderCreated events

### 2. Payment Processing [semantic-anchor: scenario.payment-processing]
- **Esper**: EPL rule to correlate OrderCreated with PaymentReceived
- **Flink**: Keyed stream processing to join events
- **Flink CEP**: Pattern to detect OrderCreated followed by PaymentReceived

### 3. Payment Timeout Detection [semantic-anchor: scenario.payment-timeout]
- **Esper**: Timer-based rule to detect missing PaymentReceived within timeout
- **Flink**: Window-based processing with state
- **Flink CEP**: Pattern with timeout for payment completion

### 4. Order Cancellation [semantic-anchor: scenario.order-cancellation]
- **Esper**: Rule to detect OrderCancelled and handle refund logic
- **Flink**: Stateful processing to handle cancellation
- **Flink CEP**: Pattern for order lifecycle including cancellation

### 5. Shipment Start [semantic-anchor: scenario.shipment-start]
- **Esper**: Rule to validate ShipmentStarted follows successful payment
- **Flink**: State validation in stream processing
- **Flink CEP**: Pattern for complete order-to-shipment flow

## Risk Mitigations

| Risk | Mitigation | Status |
|------|------------|--------|
| Too much code duplication | Extract truly common utilities to event-model, use consistent patterns | ✅ Implemented |
| Implementations diverge | Document comparison points, maintain consistent scenarios | ✅ Planned |
| Maintenance burden too high | Keep modules focused and minimal, document relationships | ✅ Implemented |
| Inconsistent behavior | Use shared event model, implement same test scenarios for each | ✅ Planned |

## Comparison Focus Areas

When comparing implementations, focus on:

### 1. Rule/Pattern Definition
- **Esper**: EPL (Event Processing Language) syntax
- **Flink**: DataStream API and operators
- **Flink CEP**: Pattern API and pattern definitions

### 2. State Management
- **Esper**: Automatic state management, windowing
- **Flink**: Manual state, checkpointing, savepoints
- **Flink CEP**: Pattern state management

### 3. Time Handling
- **Esper**: Event time, processing time, timer events
- **Flink**: Event time, processing time, watermarks
- **Flink CEP**: Time windows, timeouts in patterns

### 4. Performance Characteristics
- Throughput under load
- Latency for event processing
- Memory usage and state size
- CPU utilization

### 5. Operational Complexity
- Deployment requirements
- Configuration complexity
- Monitoring capabilities
- Failure recovery

### 6. Development Experience
- Code clarity and readability
- Debugging capabilities
- Testing approaches
- Error handling
